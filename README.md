# Oil Production DWH — база данных нефтедобычи

Учебный проект по проектированию баз данных и SQL-аналитике на предметной области
нефтедобычи: месторождения, кусты, скважины, суточная добыча и закачка,
геолого-технические мероприятия (ГТМ) и график буровых установок.

Данные **синтетические**, но сгенерированы по физически осмысленной модели
(падение дебита по Арпсу, рост обводнённости, износ насосов, эффект от ГТМ), поэтому
аналитика даёт правдоподобные отраслевые выводы. Проект поднимается одной командой.

**Стек:** PostgreSQL 16 · ClickHouse 26.8 · Apache Airflow 3.3 · Apache Superset 6.1 · SQL · Python · Docker Compose

```
PostgreSQL (OLTP)  ──►  Airflow DAG  ──►  ClickHouse (DWH, «звезда»)  ──►  Superset (дашборд)
 источник, 3НФ          месяц за месяцем    факты + измерения + витрины     «дашборд как код»
                        со сверкой
```

![Дашборд Superset](docs/dashboard.png)

## Что демонстрирует проект

- **Проектирование схемы** в 3НФ с целостностью на уровне БД: составные внешние ключи,
  `CHECK`, исключающие ограничения `EXCLUDE` (буровая не может стоять на двух кустах
  одновременно, ГТМ на скважине не пересекаются по датам)
- **Партиционирование** таблицы фактов по годам и проверку отсечения партиций
- **Индексы под конкретные сценарии:** BRIN с подобранным `pages_per_range`,
  PK как индекс для точечных выборок, индексы на внешних ключах
- **Материализованное представление** с обновлением без блокировки читателей
- **Аналитический SQL:** оконные функции, `LATERAL`, «острова и пропуски»,
  `ROLLUP` / `GROUPING`, `FILTER`, операции с диапазонами дат
- **Проверки качества данных** для правил, которые не выражаются ограничениями схемы
- **Замеры производительности** через `EXPLAIN ANALYZE` — с честными выводами,
  см. [docs/performance.md](docs/performance.md)
- **Хранилище «звезда» в ClickHouse** и **ETL на Airflow**: идемпотентная загрузка
  с атомарной подменой партиций, backfill истории, сверка с источником до последнего
  знака, сравнение с PostgreSQL — см. [docs/clickhouse.md](docs/clickhouse.md)
- **Дашборд в Superset как код:** подключение, датасеты, метрики, графики, раскладка
  и фильтры создаются скриптом через REST API — см. [docs/superset.md](docs/superset.md)
- **SCD Type 2 в DAG:** задача `build_dim_well_scd` сравнивает текущие версии
  атрибутов скважин с источником и закрывает/открывает версии при переводах под
  закачку и сменах пласта (`scripts/scd_loader.py`, `scripts/scd_builder.py`)
- **Профилирование и контроль качества в DAG:** задача `profile_after_load` считает
  распределения (null%, кардинальность, skewness, IQR), сравнивает их KS-тестом и
  сверяет количество строк и суммы — см. [scripts/profile_columns.py](scripts/profile_columns.py)
- **dbt для трансформаций:** слой staging (стандартизация имён и типов) и marts
  (бизнес-логика: обводнённость, decline rate, компенсация) описаны моделями dbt.
  `dbt build` строит витрины и запускает тесты (not_null, unique, accepted_values,
  custom assertions) за один запуск — см. [dbt/](dbt/)

## Data Modeling & Quality Decisions

### Почему «звезда», а не «снежинка»

В ClickHouse иерархия (месторождение → куст → пласт → скважина) схлопнута в одну
dimension-таблицу `dim_well`. Снежинка (отдельные dim_field, dim_pad, dim_formation)
дала бы 3 лишних JOIN в каждом отчёте. В колоночном хранилище денормализация —
стандартная практика: читаем меньше таблиц, быстрее.

### SCD Type 1 vs Type 2

| Тип | Где | Когда использовать |
|---|---|---|
| **Type 1** (перезапись) | `dim_well` | Атрибут исправлен (опечатка), старое значение не важно |
| **Type 2** (версия) | `dim_well_scd` | Атрибут **изменился по делу**: скважина переведена под закачку |

SCD 2 добавляет `valid_from` / `valid_to` / `is_current` и surrogate key.
Интервал **полуоткрытый**: `valid_from <= d < valid_to` — поэтому закрытая версия
и новая стыкуются в одну дату без дыр и пересечений. Присоединение факта к версии:

```sql
JOIN dwh.dim_well_scd AS d
  ON f.well_id = d.well_id
 AND f.prod_date >= d.valid_from
 AND f.prod_date <  d.valid_to
```

Логика версий вынесена в `scripts/scd_builder.py` и проверяется тестами:
одна текущая версия на скважину, нет пересечений и разрывов, point-in-time lookup,
детерминированный surrogate key (повторный прогон не плодит версии).

### Контроль качества данных в ETL

| Проверка | Как | Что ловит |
|---|---|---|
| Null% | `count(null)/count(*)` | Внезапный рост пропусков → проблема источника |
| Кардинальность | `count(distinct)` | Дубликаты, потеря уникальности |
| Skewness / IQR | `scipy.stats.skew`, `np.percentile` | Аномалии распределения, выбросы |
| Константа | `unique == 1` | Заливка дефолтного значения вместо данных |
| **Сверка количества строк** | `count(source) vs count(target)` | Потеря и дублирование строк |
| **Сверка сумм** | `sum(metric) source vs target` | Подмена значений, обрезка хвоста |
| KS-тест | `scipy.stats.ks_2samp` | Изменилась **форма** распределения |

**Про KS-тест — честно:** он сравнивает форму распределения, а не количество строк.
Проверено на 200 000 строк:

| Сценарий | KS |
|---|---|
| потеряли 5 % строк случайно | пропустил |
| задвоили 10 % строк | пропустил |
| сдвиг среднего на 0,5 % | поймал (p ≈ 0, ks = 0,014) — ложная тревога |
| 1 % строк заменён нулями | поймал |

Поэтому KS не единственный контроль: потерю и дублирование ловит сверка количества
строк, подмену значений — сверка сумм, а ложные срабатывания на больших объёмах
отсекает порог по силе эффекта (`ks_stat >= 0,02`), а не только p-value.

### Как это работает в DAG

```
refresh_reference ──► build_dim_well_scd
        │
        ├──► load_production ──┐
        └──► load_injection  ──┴──► build_mart ──► reconcile ──► profile_after_load
                                                            │
                                                    dbt build (после DAG)
                                                    ├── staging: стандартизация
                                                    └── marts: бизнес-логика + тесты
```

### dbt: трансформации отдельно от загрузки

Airflow загружает сырые данные (facts, dimensions) — dbt строит витрины поверх них.
Это разделение ответственности (ELT, не ETL): оркестрация и загрузка в Airflow,
трансформация и тестирование в dbt.

```
dbt/oil_production/
├── models/
│   ├── staging/              # view: стандартизация имён и типов → база dwh_staging
│   │   ├── stg_production_daily.sql
│   │   ├── stg_injection_daily.sql
│   │   └── stg_dim_well.sql
│   └── marts/                # table: бизнес-логика → база dwh_marts
│       ├── mart_field_monthly.sql      # добыча × месторождение × месяц
│       └── mart_well_performance.sql   # decline, watercut, дебит по скважинам
├── tests/
│   ├── assert_oil_non_negative.sql
│   ├── assert_watercut_bounds.sql
│   ├── assert_well_exists_in_dim.sql
│   ├── assert_mart_matches_facts.sql   # витрина не теряет строки фактов
│   └── assert_mart_grain_unique.sql    # одна строка на месторождение × месяц
├── schema.yml
└── dbt_project.yml
```

**Формулы совпадают с витриной Airflow** — иначе сверка двух реализаций бессмысленна:

```
liquid_m3    = oil_t * 1000 / oil_density + water_m3   (тонны → м³ по плотности)
watercut     = water_m3 / liquid_m3
compensation = injection_m3 / liquid_m3
```

Проверка на данных за 2021-01: `oil_t` = 172 446,7 у обоих путей, `watercut` = 0,3344
у обоих, расхождение сумм — 0. Задача `reconcile` сверяет `dwh.mart_field_monthly`
(Airflow) с `dwh_marts.mart_field_monthly` (dbt) и падает при расхождении больше 0,01.

**Как запускать:**

```bash
docker compose run --rm dbt      # ждёт данные в ClickHouse (до 10 минут) и делает dbt build
docker compose up -d dbt         # то же, но сервисом
```

`dbt build` = модели + тесты за один прогон: собрать витрину с битыми данными нельзя.
Документация и lineage — `dbt docs generate` / `dbt docs serve`.

**Тесты:**

| Тест | Тип | Что проверяет |
|---|---|---|
| `not_null` на ключевых колонках | стандартный | Нет пропусков в ключах и метриках |
| `unique` на `well_id` в измерении | стандартный | Нет дубликатов скважин |
| `accepted_values` на purpose, trajectory | стандартный | Только известные категории |
| `assert_oil_non_negative` | кастомный | Добыча ≥ 0 |
| `assert_watercut_bounds` | кастомный | Обводнённость ∈ [0, 1] при liquid > 0 |
| `assert_well_exists_in_dim` | кастомный | Каждый факт имеет измерение |
| `assert_mart_matches_facts` | кастомный | Суммы витрины = суммы фактов |
| `assert_mart_grain_unique` | кастомный | Нет дублей по (месяц, месторождение) |

**CI:** отдельный workflow `dbt.yml` поднимает ClickHouse сервис-контейнером,
загружает `dbt/ci_seed.sql` и запускает `dbt build` — ошибки компиляции и тесты
ловятся до мержа.

**Ограничение, о котором честно:** витрина `mart_field_monthly` пока строится двумя
путями — задачей `build_mart` в Airflow и моделью dbt. Это переходный период: числа
сверяются, но источник правды один — после удаления `build_mart` из DAG останется dbt.

- `build_dim_well_scd` берёт актуальные атрибуты из PostgreSQL, сравнивает с текущими
  версиями в ClickHouse и пишет только изменения. Дата версии — **день запуска**, а не
  месяц данных: исторического источника атрибутов нет, и это записано в docstring.
  После вставки выполняется `OPTIMIZE ... FINAL`, иначе `ReplacingMergeTree` покажет
  и старую, и новую версию строки.
- `profile_after_load` — распределения и сверки за месяц; при материальном
  расхождении задача падает и останавливает контур.

### Если стенд уже поднимался

Init-скрипты ClickHouse выполняются только на **пустом** томе. Если `chdata` остался
от прошлых запусков, таблица SCD не создастся — примените DDL вручную:

```bash
docker compose exec -T clickhouse clickhouse-client --multiquery < clickhouse/init/02_scd.sql
```

Либо начните с чистого тома: `docker compose down -v`.

### Что ещё не сделано

- **Исторические атрибуты скважин.** SCD пишет версии с даты запуска: если атрибут
  менялся в прошлом, восстановить это из текущего источника нельзя — нужен CDC или
  архивные срезы.
- **Мягкие удаления.** Скважина, пропавшая из источника, версию не закрывает —
  это осознанное упрощение, чтобы не терять историю при сбое выгрузки.

## Быстрый старт

Нужен только Docker (рекомендуется выделить ему от 6 ГБ памяти).

```bash
git clone https://github.com/Alex91132/oil-production-dwh.git
cd oil-production-dwh
docker compose up -d --build
```

Что произойдёт:
1. PostgreSQL создаёт схему, генератор наполняет её (~30 с, ≈540 тыс. строк добычи).
2. ClickHouse создаёт схему хранилища.
3. Airflow стартует и сам загружает в хранилище всю историю — 69 месячных запусков
   (~3 мин). Ход загрузки — в интерфейсе Airflow: http://localhost:8080.
4. Superset поднимается, и скрипт создаёт дашборд:
   http://localhost:8088/superset/dashboard/oil-production/

Весь стек с нуля готов примерно за 4 минуты.

| Сервис | Адрес | Доступ |
|---|---|---|
| PostgreSQL (источник) | `localhost:5435`, база `oilfield` | `dwh` / `dwh` |
| ClickHouse (хранилище) | `localhost:8123`, база `dwh` | `dwh` / `dwh` |
| Airflow | http://localhost:8080 | без пароля (локальный стенд) |
| Superset | http://localhost:8088 | `admin` / `admin` |

Запустить любой аналитический запрос к источнику:

```bash
docker compose exec db psql -U dwh -d oilfield -f /sql/analytics/04_intervention_effect.sql
```

> подменит путь `/sql/...` на путь Windows. В PowerShell и Linux/macOS команда работает как есть.

Запрос к хранилищу:


Открыть консоль: `docker compose exec db psql -U dwh -d oilfield` или

Учётные данные только для локального стенда; меняются в `.env` (см. `.env.example`).

## Модель данных

```mermaid
erDiagram
    fields ||--o{ formations : "содержит пласты"
    fields ||--o{ pads : "содержит кусты"
    pads ||--o{ wells : "на кусте"
    formations ||--o{ wells : "вскрывает пласт"
    wells ||--o{ daily_production : "суточная добыча"
    wells ||--o{ daily_injection : "суточная закачка"
    wells ||--o{ interventions : "ГТМ"
    intervention_types ||--o{ interventions : "вид"
    rigs ||--o{ rig_assignments : "график"
    pads ||--o{ rig_assignments : "бурится"

    wells {
        int well_id PK
        smallint field_id FK
        int pad_id FK
        smallint formation_id FK
        enum purpose "добывающая / нагнетательная"
        enum trajectory "ННС / ГС / МЗС"
        date spud_date
        date start_date
    }
    daily_production {
        int well_id PK, FK
        date prod_date PK "партиции по годам"
        numeric hours_on
        numeric oil_t
        numeric water_m3
        numeric gas_km3
    }
    interventions {
        int intervention_id PK
        int well_id FK
        text type_code FK
        date start_date
        date end_date
        numeric cost_mln_rub
    }
    rig_assignments {
        int assignment_id PK
        smallint rig_id FK
        int pad_id FK
        date start_date
        date end_date
    }
```

Ключевые решения:

| Решение | Зачем |
|---|---|
| `field_id` в `wells` + составные FK `(field_id, pad_id)` и `(field_id, formation_id)` | гарантирует, что куст и пласт скважины принадлежат одному месторождению — без триггеров |
| `EXCLUDE USING gist (rig_id WITH =, daterange(...) WITH &&)` | физическое ограничение «одна буровая — один куст» проверяет сама БД |
| `ENUM` для назначения и типа ствола, отдельная таблица для видов ГТМ | стабильные наборы — `ENUM`; справочник с атрибутами (категория, название) — таблица |
| Партиции `daily_production` по годам + `DEFAULT`-партиция | отсечение партиций в запросах за период, простая архивация старых лет |
| Добыча в т, вода в м³, газ в тыс. м³ | единицы, принятые в отраслевой отчётности |

## Что показывают данные

- **ЗБС даёт максимальный прирост (+20 т/сут), но тонна доп. нефти у него самая дорогая**
  (~30 тыс. ₽). Самая дешёвая тонна — у ОПЗ (~5,7 тыс. ₽), но он успешен лишь в 57 % случаев;
  ГРП даёт в 4 раза больший прирост при сопоставимой цене тонны (~7,8 тыс. ₽) (запрос 04)
- **Многозабойные скважины на старте дают в 3–4 раза больше наклонно-направленных** —
  на новом месторождении 192 против 61 т/сут (запрос 11)
- **Компенсация отборов:** на зрелых месторождениях перекомпенсация (135–215 %),
  а на растущем «Таёжном» — дефицит закачки (~70 %): нужно больше нагнетательных
  скважин (запрос 08)
- **Добыча держится на меньшинстве фонда:** 11 % скважин дают половину нефти,
  30 % — 80 % (запрос 07)
- **Аварийные простои на новом месторождении стоят дороже всего:** 118 тыс. т
  недобора против 32–45 тыс. т на зрелых — там выше дебиты (запрос 06)
- **Эффект ГРП живёт около года:** дебит удваивается в первый месяц, а к 12-му
  возвращается к исходному уровню; после ОПЗ через год дебит даже ниже исходного
  (ClickHouse, запрос 02 с `ASOF JOIN`)

## Хранилище и загрузка (Этап 2)

Подробно — в [docs/clickhouse.md](docs/clickhouse.md). Коротко:

- **Схема «звезда»:** `dim_well`, `dim_date`, факты суточной добычи, закачки и ГТМ,
  витрина «месторождение × месяц» для дашборда.
- **DAG `oil_dwh_monthly_load`:** один запуск — один месяц. Месяц собирается
  в промежуточной таблице и атомарно подменяет партицию (`REPLACE PARTITION`),
  поэтому повторы и ретраи не создают дублей. После загрузки — сверка с PostgreSQL
  по числу строк и точным суммам.
- **Результат:** 538 437 строк и 13 944 830,318 т нефти — совпадение с источником
  до последнего знака.
- **Сравнение с PostgreSQL:** тяжёлый агрегат в 3–20 раз быстрее (в зависимости от
  `count(DISTINCT)`), хранение в ~5 раз компактнее. Подробные замеры и оговорки —
  в документации.
- **Найденный подвох Airflow 3:** `schedule="@monthly"` по умолчанию даёт запуски
  без интервала данных. Ошибку поймала защита ClickHouse от подмены партиции из
  пустого источника; решено явным `CronDataIntervalTimetable` и проверкой интервала.

## Дашборд (Этап 3)

Подробно — в [docs/superset.md](docs/superset.md). Коротко:

- **8 графиков:** KPI с трендом (добыча, фонд, обводнённость), динамика по
  месторождениям, компенсация отборов, ГТМ по видам и годам, таблица затухания
  эффекта ГТМ. Фильтры по месторождению и периоду.
- **Дашборд как код:** [`superset/bootstrap/create_dashboard.py`](superset/bootstrap/create_dashboard.py)
  создаёт всё через REST API Superset при первом запуске стека; изменения дашборда
  идут через git, а не через клики.
- **Проверено:** значения KPI сверены с прямыми запросами к ClickHouse, фильтры
  применяются ко всем графикам, полный подъём с нуля создаёт дашборд автоматически.
- **Методические детали:** медианы точные (приближённая `median` в ClickHouse давала
  «плавающий» результат); у обводнённости убрано сравнение «+14,5 % к прошлому году»,
  которое легко принять за процентные пункты (на деле +6,4 п.п.).

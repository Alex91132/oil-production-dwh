# Производительность: решения и замеры

Все замеры — `EXPLAIN (ANALYZE)` на PostgreSQL 16 в Docker, тёплый кэш,
~540 тыс. строк суточной добычи (≈100 тыс. на годовую партицию).
Абсолютные миллисекунды зависят от машины — важны соотношения.

## 1. Партиционирование суточной добычи по годам

Запрос за март 2025 читает **только партицию 2025** — остальные годы отсекаются
ещё на этапе планирования (partition pruning):

```
Aggregate
  ->  Bitmap Heap Scan on daily_production_2025
        ->  Bitmap Index Scan on daily_production_2025_prod_date_idx
```

Зачем ещё: старые годы можно отключить (`DETACH PARTITION`) и унести в архив
без `DELETE` миллионов строк; `VACUUM` и обслуживание идут по партициям.
Страховочная `DEFAULT`-партиция ловит строки вне ожидаемых лет — проверка
качества данных следит, чтобы она оставалась пустой.

## 2. BRIN вместо B-tree для диапазонов дат

Запрос «все скважины за месяц» (партиция 2025, 8 414 строк из 99 тыс.):

| Вариант | Размер индекса | Время | Комментарий |
|---|---|---|---|
| Без индекса (Seq Scan) | — | 5,2 мс | читается вся партиция |
| B-tree по `prod_date` | 752 КБ | 1,6 мс | |
| BRIN, `pages_per_range = 128` (по умолчанию) | 24 КБ | 3,0–3,5 мс | 24 276 лишних строк на перепроверке |
| **BRIN, `pages_per_range = 32`** | **24 КБ** | **1,75 мс** | 3 838 лишних строк |

**Почему BRIN работает:** генератор загружает данные в хронологическом порядке,
и физический порядок строк идеально совпадает с датой:

```sql
SELECT attname, correlation FROM pg_stats
WHERE tablename = 'daily_production_2025';
-- prod_date | 1.000
-- well_id   | 0.048
```

BRIN хранит только min/max даты для каждого блока страниц, поэтому он в ~30 раз
меньше B-tree. Цена — «грубость»: читаются целые блоки, лишние строки
отбрасываются перепроверкой. Уменьшение `pages_per_range` до 32 сделало блоки
мельче — лишних строк в 6 раз меньше, скорость сравнялась с B-tree.

**Честный вывод:** на текущем объёме выигрыш BRIN — в размере и стоимости
вставки, а не в скорости. Он становится решающим на сотнях миллионов строк,
где B-tree по дате занимал бы гигабайты и замедлял каждую загрузку.

**Когда BRIN не подойдёт:** если данные приходят вразнобой (поздние досылки,
исправления задним числом), корреляция падает и BRIN деградирует до полного
просмотра. Тогда нужен B-tree или периодический `CLUSTER`.

## 3. Материализованное представление месячной добычи

Месячная добыча всех скважин за 2025 год:

| Источник | Читается строк | Время |
|---|---|---|
| Агрегат «на лету» из `daily_production` | 99 232 | 36,4 мс |
| `mv_monthly_production` | 3 275 | 1,2 мс |

Ускорение ~**30 раз**: агрегат считается один раз при обновлении, отчёты читают
готовый результат. Уникальный индекс `(well_id, month)` позволяет обновлять
представление командой `REFRESH MATERIALIZED VIEW CONCURRENTLY` — без блокировки
читателей. Цена — данные актуальны на момент последнего обновления, поэтому
обновление встроено в конец загрузки.

## 4. Точечные выборки по скважине

Запрос «дебит скважины за 30 суток» — основа анализа эффекта ГТМ
(`sql/analytics/04_intervention_effect.sql` выполняет его дважды на каждое
мероприятие через `LATERAL`):

```
Bitmap Index Scan on daily_production_2025_pkey  (rows=30)
Execution Time: 0.108 ms
```

Первичный ключ `(well_id, prod_date)` сразу служит индексом под этот сценарий —
отдельный индекс не нужен. Порядок колонок важен: сначала `well_id`
(равенство), затем `prod_date` (диапазон).

## 5. Индексы на внешних ключах

PostgreSQL не создаёт индексы на ссылающейся стороне FK автоматически.
Без них удаление или изменение родительской строки (например, куста) приводит
к полному просмотру дочерней таблицы. Поэтому индексы созданы явно:
`wells(pad_id)`, `wells(formation_id)`, `rig_assignments(pad_id)`,
`interventions(well_id, start_date)`.

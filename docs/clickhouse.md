# Этап 2: хранилище в ClickHouse и загрузка через Airflow

```
PostgreSQL (OLTP, ops.*)  ──►  Airflow DAG oil_dwh_monthly_load  ──►  ClickHouse (dwh.*)
   нормализованная модель        1 запуск = 1 месяц данных             схема «звезда»
```

## Схема «звезда»

| Таблица | Тип | Зерно | Движок, ключи |
|---|---|---|---|
| `dim_date` | измерение | день | календарь 2010–2030, заполняется при создании |
| `dim_well` | измерение | скважина | иерархия «месторождение → куст → пласт» схлопнута в одну таблицу |
| `fact_production_daily` | факт | скважина × сутки | `MergeTree`, `PARTITION BY toYYYYMM(prod_date)`, `ORDER BY (well_id, prod_date)` |
| `fact_injection_daily` | факт | скважина × сутки | так же |
| `fact_interventions` | факт | мероприятие | атрибуты вида ГТМ денормализованы в факт |
| `mart_field_monthly` | витрина | месторождение × месяц | добыча, обводнённость, компенсация — готово для дашборда |

Суммы хранятся в `Decimal`, а не во `Float`: только так сверку с источником
можно делать на точное равенство, а не «примерно совпадает».

## DAG `oil_dwh_monthly_load`

```
refresh_reference ─┐
load_production ───┼──► build_mart ──► reconcile
load_injection ────┘
```

| Задача | Что делает |
|---|---|
| `refresh_reference` | перезаливает `dim_well` и `fact_interventions`: заполняет копию и атомарно меняет местами (`EXCHANGE TABLES`) |
| `load_production`, `load_injection` | собирают месяц в промежуточной таблице и атомарно подменяют партицию факта (`REPLACE PARTITION`) |
| `build_mart` | строит месяц витрины тем же способом |
| `reconcile` | сравнивает с источником число строк и точные суммы; при расхождении падает |

**Идемпотентность.** Каждая задача перезаписывает только свою месячную партицию.
Повтор запуска или автоматический ретрай не создают дублей, а параллельные запуски
разных месяцев (`max_active_runs=3`) не мешают друг другу. Проверено: повторный
запуск марта 2025 оставил 8 414 строк и те же суммы, обновилось только время загрузки.

**Backfill.** `catchup=True` с `start_date` 2021-01-01: после первого старта DAG
сам загружает всю историю — 69 месяцев примерно за 2,5 минуты.

### Найденная ошибка, которую стоит знать

Первый запуск упал на всех месяцах. Оказалось, в **Airflow 3 строка
`schedule="@monthly"` по умолчанию даёт запуски без интервала данных**
(`[scheduler] create_cron_data_intervals = False`): `data_interval_start` равен
`data_interval_end`. Фильтр `prod_date >= start AND prod_date < end` возвращал
0 строк.

Данные не потерялись благодаря проверке **ClickHouse 26**: он отказался
выполнять `REPLACE PARTITION` из пустой промежуточной таблицы, потому что иначе
молча стёр бы данные в целевой партиции. Ошибка проявилась сразу, а не через
месяц в отчётах.

Исправление:
- явное интервальное расписание `CronDataIntervalTimetable("@monthly")`;
- защита в коде: при пустом интервале задача падает с понятным сообщением.

После загрузки всей истории:

| | Строки добычи | Нефть, т | Строки закачки | Закачка, м³ | Скважин | ГТМ |
|---|---|---|---|---|---|---|
| PostgreSQL | 538 437 | 13 944 830,318 | 127 080 | 30 864 688,026 | 378 | 676 |
| ClickHouse | 538 437 | 13 944 830,318 | 127 080 | 30 864 688,026 | 378 | 676 |

Перекрёстная проверка логики: топ-5 скважин каждого месторождения в ClickHouse
(`LIMIT BY`) и в PostgreSQL (`RANK() OVER`) совпали по всем 15 строкам.

## PostgreSQL vs ClickHouse: честное сравнение

Запрос: годовая добыча по месторождениям за всю историю — агрегат по 538 тыс.
строк с JOIN к справочнику. Лучшее из трёх прогонов, тёплый кэш.

| Вариант запроса | PostgreSQL 16 | ClickHouse 26.8 | Разница |
|---|---|---|---|
| суммы + число уникальных скважин | ~805 мс | ~40 мс | ~20× |
| только суммы | ~115 мс | ~40 мс | ~3× |

| Хранение суточной добычи | Объём |
|---|---|
| PostgreSQL, данные | 34 МБ |
| PostgreSQL, данные + индексы | 50 МБ |
| ClickHouse, сжато | 6,3 МиБ (без сжатия 19,5 МиБ, сжатие 3,1×) |

**Выводы:**
- Разница «в 20 раз» во многом связана с `count(DISTINCT)`: в PostgreSQL он требует
  сортировки, а `uniqExact` в ClickHouse работает на хеш-таблице. Без него разница
  около 3 раз — на таком маленьком объёме PostgreSQL с параллельным сканированием
  справляется хорошо.
- Столбцовое хранение читает только нужные колонки и хорошо сжимается: объём
  в ~5 раз меньше без индексов.
- Преимущество ClickHouse растёт с объёмом данных. На полумиллионе строк
  PostgreSQL ещё достаточно; хранилище оправдано при сотнях миллионов строк,
  тяжёлых агрегатах и множестве одновременных аналитических пользователей.

## Запросы к хранилищу

Каждый показывает возможность ClickHouse, которой нет в PostgreSQL.
Результаты — [analytics_results_clickhouse.md](analytics_results_clickhouse.md).

| # | Вопрос | Особенность ClickHouse |
|---|---|---|
| 01 | Топ-5 скважин каждого месторождения | `LIMIT n BY` вместо оконной функции |
| 02 | Как затухает эффект каждого вида ГТМ через 1/3/6/12 месяцев | `ASOF JOIN` (последнее ГТМ перед датой), комбинатор `medianExactIf` |
| 03 | Распределение стартовых дебитов по типу ствола | `quantilesExact`, `argMax`, `arrayMap` |

Медианы и квантили — **точные** (`*Exact`). Обычные `median` / `quantiles` в ClickHouse
приближённые: считаются по выборке и могут отличаться между запусками. Это
обнаружилось при сверке дашборда с прямым запросом (1,26 против 1,25) — для
отчётности такое недопустимо.
| 04 | Сводка для дашборда: добыча, обводнённость, компенсация, итог с начала года | витрина + оконная функция |

Главный вывод запроса 02: эффект ГРП (дебит ×2 в первый месяц) почти полностью
исчезает к 12-му месяцу, а после ОПЗ через год дебит даже ниже исходного:
естественное падение перекрывает слабый эффект.

## Как посмотреть

- Интерфейс Airflow: http://localhost:8080 (локальный стенд, вход без пароля)
- Консоль ClickHouse: `docker compose exec clickhouse clickhouse-client -u dwh --password dwh`
- Запрос из файла:
  `docker compose exec clickhouse clickhouse-client -u dwh --password dwh --queries-file /sql/clickhouse/02_intervention_decay_asof.sql`
- HTTP-интерфейс: `http://localhost:8123` (пользователь и пароль `dwh`)
